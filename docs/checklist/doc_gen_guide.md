# checklist/ 문서 작성 가이드

이 폴더의 `doc_gen_guide.md`는 Git으로 배포하는 작성 안내다. 실제 과업 문서는 같은 폴더에 작성하며 Git 추적·공개본에서 제외한다. 기존 로컬 문서도 지우지 않는다.

공통 규칙의 정본은 [문서발행규칙](../../rules/docs.md), 수행·승인·검증의 정본은 [작업수행규칙](../../rules/workflow.md)이다. 이 가이드는 실제 과업 기록이나 승인 근거가 아니다.

## 역할과 작성 시점

Planner가 구현 전에 완료 기준과 검사 항목 초안을 만들고, Validator가 실제 관측·근거·판정을 채운다. 구현 결과에 맞춰 합격 기준을 낮추지 않는다.

checklist는 현재 판정의 원장이다. 일지가 아니다. 항목 하나가 관측 가능한 결과 하나이고 행 하나다. 판정이 바뀌면 그 행을 고친다. 무슨 일이 있었는지는 devlog에 적고 여기에 절을 쌓지 않는다. 아직 해소되지 않은 `FAIL`과 `NOT_RUN`은 그 행에 그대로 둔다.

대화 이력이 없는 사람이 이 문서와 plan만 읽고 검사를 따라 할 수 있게 쓴다. 작성자에게 물어야 실행할 수 있는 명령은 다시 쓴다.

## 반드시 담을 내용

- 각 항목의 검사 명령, 기대값, 검사 대상·환경·입력. 기대값은 통과와 실패를 가를 수 있는 값으로 적는다.
- 실제 관측·종료 결과·원시 근거 위치와 검사 상태.
- 적용하지 않는 항목은 `NOT_APPLICABLE`과 사유. 사유 없는 `N/A`나 `TBD`로 칸을 비워 두지 않는다.
- 자체검사, 독립 검토, 실제 통합·기동·정상/경계/실패 시나리오, 성능, 최종 수용의 적용 여부.
- 독립 검증이 필요하면 검증 주체·범위·지적과 재검증 결과.
- 잔여 실패·미실행·제약·후속 조치와 사용자 수용 여부.

## 검사 상태

| 상태 | 의미 |
|---|---|
| PASS | 정의한 검사를 해당 대상에서 실행해 통과 |
| FAIL | 실행 결과가 기준 위반 |
| NOT_RUN | 아직 또는 환경·권한 문제로 미실행 |
| NOT_APPLICABLE | 적용 대상이 아님. 사유 기록 |
| STALE | 대상·환경·기준 변경으로 현재 판정에 재사용 불가 |

## 검사 항목 예시

```markdown
| ID | 결과 | 명령 | 기대값 | 관측 | 근거 | 상태 |
|---|---|---|---|---|---|---|
| C1 | 승인한 API의 응답이 변환 전과 같다 | <대상과 환경에서 실행할 명령> | <통과일 때만 나오는 출력이나 값> | <실행 후 기입> | <로그 경로> | NOT_RUN |
```

일반 완료는 모든 적용 항목과 필요한 독립 검증의 충족이다. 미해결 항목을 사용자가 대상·잔여 범위로 명시 승인한 종료는 예외 승인 종료로 적는다. 검사 결과·리뷰 판단·사용자 수용을 구분하며 승인받지 않은 수용을 만들지 않는다.

## 새 맥락 검토

plan과 checklist 초안을 발행할 때 새 맥락 검토를 한다. 검토자는 대화 이력 없이 plan, checklist, interview, 저장소만 읽는다. 검토자는 문서를 고치지 않고 지적 목록을 낸다. 결과는 "독립 검증" 절에 회차별로 적는다.

종료 규칙의 정본은 [작업수행규칙](../../rules/workflow.md)의 "검토의 종료"다. 요점은 다음과 같다.

- 차단은 완료 기준·보존 계약·권한을 어기거나 결과가 틀린 경우이고, 어긴 기준의 위치와 재현을 함께 적은 것만 차단이다.
- 차단 지적이 없으면 그 회차로 닫는다. 비차단 지적은 기록만 하고, 검토 중에는 고치지 않는다. 고친다면 닫은 뒤 자기 점검으로 고치고 회차를 열지 않는다.
- 차단 지적을 고친 뒤에만 다음 회차를 연다. 2회차부터는 검토자 하나가 앞 회차 차단의 해소와 그 수정의 회귀만 본다. 늦게 발견한 다른 문제는 비차단 잔여다.
- 결론이 난 지적은 다시 열지 않는다. 검토자가 실행되지 않았으면 통과로 세지 않는다.
- 구현 검토는 기본이 아니다. 작업수행규칙의 사유가 있을 때만 plan에 그 사유와 함께 넣는다.
- **회차 상한은 3이다.** 상한은 채울 목표가 아니다. 상한에 닿거나 같은 지적과 수정이 되풀이되면 통과로 치지 않고 남은 지적을 정리해 사용자에게 넘긴다. 상한을 넘겨 계속하려면 사용자의 명시 승인이 필요하다.

```markdown
| 회차 | 검토자 | 실행 | 차단 지적 | 비차단 지적 | 처리 |
|---|---|---|---|---|---|
| 1 | <새 맥락의 서브에이전트> | 실행함 | 0건 | 2건 | 차단 없음. 이 회차로 닫음 |
```

2계층 과업은 이 문서에 통합 검증과 수용만 적는다. 통합 검증은 캠페인의 마지막 전체 검증의 결과다. 멈춘 항목과 gate에서 확인되지 않은 검사는 그 상태 그대로 적는다. 항목별 검사와 검토 기록은 캠페인 인스턴스에 있다.

## 작성과 갱신

- 파일명은 `<YYMMDDHH>_<한글제목>.md`이며 실제 Asia/Seoul 발행 시각을 사용한다. 같은 역할 폴더의 같은 시간대에 이미 발행한 문서가 있으면 `<YYMMDDHH_MM_SS>_<한글제목>.md`로 충돌을 피한다. 역할 접두사를 붙이지 않는다.
- 한 루프 안의 후속 기록은 같은 `task_id`와 기존 파일 경로에서 갱신한다. `updated`와 본문 변경 이력에 변경 시점·이유를 남기며 과거 승인·실패 기록을 보존한다.
- 루프가 닫힌 뒤의 후속 작업은 사용자의 요청이나 승인으로 네 문서를 새로 발행한다. 새 묶음은 새 `task_id`를 받고 `previous_task_id`로 이전 묶음을 가리킨다.
- frontmatter의 `related_*`는 저장소 상대 전체 경로, 본문의 클릭 링크는 이 문서 위치에서 해석되는 상대 경로로 적는다.
- 발행·갱신 뒤 로컬 위키에 입고한다. 실제 명령·보호 절차는 문서발행규칙을 따른다. 이 가이드 자체는 입고 대상에서 제외한다.

```yaml
task_id: sample-refactor-261106090000

related_interview: docs/interview/26110609_예시_리팩토링.md
related_plan: docs/plan/26110609_예시_리팩토링.md
related_devlog: docs/devlog/26110609_예시_리팩토링.md
---
```
