# Rust Repack 설계 인터뷰

## 사용자 목표와 현재 단계

사용자는 어떤 원 개발언어의 로직이라도 Rust 클린코드로 이식하는 단일 책임 스킬 `Rust Repack`을 설계하려 한다. 주요 대상은 Claude/Codex Harness에 연계된 AI 생성 코드다. 이름·주석을 포함한 Rust 구현 품질을 개선하고자 한다. 먼저 지정한 로컬 자료의 맥락을 수집하고 Ouroboros 딥 인터뷰를 진행하라는 요청이다.

Rust Repack의 책임은 **Rust 변환**에 한정한다. 검수 책임은 기존 `.agents/skills/code-review`와 `.agents/skills/pr-review-toolkit`에 둔다는 사용자 결정을 유지한다. 새 리뷰 오케스트레이터·배포·원본 삭제·전역 설정 변경을 목표에 추가하지 않는다. 기존 검토 스킬의 자동 호출 여부, 변환 중 compile/format의 허용 범위 등은 아직 결정하지 않았다.

현재는 인터뷰 단계다. 스킬 구현·설치·실제 코드 이식·Seed 생성은 시작하지 않았다. 이 문서는 의도와 사실을 기록하며 후속 plan/checklist는 구현 범위가 정해질 때 작성한다. 새 과업의 task_id는 이후에도 유지한다.

### 판단축을 분리할 필요

독립 리뷰 가이드의 §2.1(119–124행)은 Builder의 자체검사와 수정 책임을 명시하면서, 독립 지적의 자기 해소와 필수 기준 완화를 금지한다. 따라서 자체검사 포함은 독립 리뷰 책임 침해와 같지 않다. 스킬 점검 가이드 G05–G07은 결과 조건·유한 재검사·실제 환경 요건을 요구하며, 이를 모든 업무 세부 절차를 헌장에 넣으라는 뜻으로 해석할 근거는 없다.

권장하는 스킬 산출물 개념은 **외부 계약을 보존하는 Rust 대체 구현과 자체검사 근거를 갖춘 검토 인계물**이다. ‘.rs 파일 생성’보다 충분하고 ‘프로젝트 전체 전환 수용’보다 좁다. 검사 종류·필수 여부·도구 부재 시 인계 가능 여부는 아직 합의하지 않았으므로 이 문구 자체를 승인된 완료 기준으로 사용하지 않는다.

예: Python JSON CLI 변환에서 Rust 내부 이름은 Rust 관례를 적용하되 JSON 키·stdout/stderr·종료 코드는 계약대로 보존한다. 스킬은 승인된 산출물과 자체검사를 담당할 수 있다. 실제 기존 런처의 호출 대상 교체, 해당 환경에서 재기동, timeout/취소/잘못된 입력 및 성능 비교는 과업 계획으로 연결한다. 호환 shim의 코드 생성은 산출물 계약에 포함할지 별도 결정하며, 코드 생성이 호스트 설정 변경 권한을 자동 부여하지 않는다.

### 과적합과 중복을 피하는 기준

- Rust 전용 스킬의 전문성 자체는 목적에 부합한다. 반면 일반 헌장이 Rust·Claude hook·한 workspace 경로를 전제하면 과적합된다. 특정 코드·언어에만 맞춘 고정 예제도 스킬의 지원 범위를 입증하지 못한다.
- Rust Repack은 서로 다른 원 언어·인터페이스의 변환 사례로, val_agent 헌장은 Rust와 무관한 TypeScript 인증 수정 등의 과업에도 같은 목표·권한·근거·수용 원칙이 적용되는지로 일반성을 점검할 수 있다. 이는 평가 설계 제안이며 실행 완료나 필수 사례 채택이 아니다.
- 같은 검사라도 선정·실행·검토 책임은 다를 수 있다. 동일한 관련 대상·환경·입력·기준의 유효 근거는 재사용하고, 관련 조건이 바뀌면 영향받은 검사를 재실행한다. 독립성을 위해 모든 명령을 무조건 두 번 실행하지 않는다.
- 원본 rust-port의 ‘드문 입력 차이는 기록으로 허용’과 폭넓은 알고리즘 교체 조항은 외부 계약 보존 합의에 맞춰 제한해야 한다. 단순 합본은 성능 극대화나 계약 보존의 근거가 아니다.
- 성능 자료의 profiling/benchmark 안내는 실측 시스템이 아니다. 속도 향상 여부는 workload·비교 환경·품질 조건을 정해 측정해야 하며 Rust 전환에서 자동 도출되지 않는다.

두 보조 검토의 사실 분석과 반론은 `temp/rust-repack-interview/boundary-assets.md`, `boundary-tradeoffs.md`에 보관했다. 이번 분석을 새 사용자 답변으로 Ouroboros에 제출하지 않았고 Seed·헌장·스킬도 변경하지 않았다. 다음 인터뷰에서는 기존 번호 선택을 재촉하기보다, 위 책임 배치와 스킬 인계 조건을 먼저 합의한다.

### 계약 보존과 충돌할 때

Rust 내부 표현은 개선하되 JSON 키·CLI 옵션·프로세스 입출력·종료 코드·기존 import/API·FFI 이름 등 외부 식별자와 의미를 자동 변경하지 않는다. 보존해야 하는 모호한 외부 이름은 경계에 남기고 내부 이름으로 대응시킬 수 있다. 최소 연결 코드는 과업에서 명시한 범위만 작성한다. 읽기 좋게 만들려면 외부 동작 변경이 필요한 경우 변환 중 임의로 결정하지 않고 미해결 요구를 반환한다.

### 완료 판단에 사용할 관측 항목 — 후보

- 주석을 가려도 주요 내부 이름과 타입에서 값의 역할·단위·상태와 함수의 책임을 이해할 수 있는가.
- 함수 분리·타입 개선이 실제 혼동을 줄였으며 상태·오류·순서 계약을 바꾸지 않았는가.
- 남은 주석이 이름·구현 복창을 넘어 필요한 계약·맥락·안전 근거를 제공하고 현재 코드와 일치하는가.
- 공개 API의 이용에 필요한 오류·부작용·전제조건과 필요한 안전 정보가 남아 있는가.
- 외부 계약을 보존했는가. 보존한 특이 동작을 임의 정정하거나 해명되지 않은 이유를 창작하지 않았는가.
- 실제 자체검사 결과와 위 의미상 판단을 구분해 반환하는가. fmt/build/Clippy 통과만으로 이름·구조·주석의 적절성을 증명했다고 주장하지 않는가.

이 항목은 주석 개수·함수 길이·타입 개수 같은 수치 목표나 모든 변경별 장문 분석 보고서를 요구하지 않는다. 공개 API 문서는 필요한 계약 내용 중심의 기본을 제안하며, BeautifulRust의 모든 pub 항목·모듈별 일괄 문서 템플릿과 고정 요약 길이를 통째 채택하는 것은 아니다. 주석 언어는 별도 미결정으로 유지한다.

### 공개 자산의 맞춤 조정

BeautifulRust는 이미 의미 중심 포팅, Rust 타입 모델링, 명명, 중복 설명 회피, 공개 API·안전성 문서를 제공한다. 따라서 ‘공개 프로젝트로는 이 방향을 수행할 수 없다’고 단정할 근거는 없다. 커스텀의 핵심은 이 강점을 기반으로 **작업 순서·충돌 우선순위·완료 관측 기준·범위와 인계 계약**을 한 스킬의 일관된 지침으로 묶는 것이다.

- BeautifulRust: 구현 절차의 기반. 기존 계약 보존과 이름/타입/책임 개선 선행을 명시하고, 일률적 문서 틀·입력 차이 허용 등 충돌 조항은 조정한다.
- rust-skills: 해당 문제에 필요한 소유권·타입·오류 설계 지식만 참고 자료로 선별한다. 광역 router/hooks·타 프로젝트 전역 규칙은 가져오지 않는다.
- rust-analyzer-mcp: 타입·참조·심볼·진단으로 변환 판단을 보조한다. 도구 사용 여부를 별도 의존성·환경 계약으로 다루며 연결 성공이나 의미상 클린코드 준수를 가정하지 않는다.

두 보조 검토는 `temp/rust-repack-interview/comment-policy-assets.md`, `comment-policy-tradeoffs.md`에 보관했다. 기존 round5 advisory를 중복 제출하거나 새 사용자 답변으로 보내지 않았다. 정책에 따른 실제 코드 변환·스킬 구현은 아직 수행하지 않았다.
