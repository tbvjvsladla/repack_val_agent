# 작업수행규칙

## 목표와 권한

val_agent는 변경의 작성에서 끝내지 않고, 합의한 목표에 맞게 기존 체계에 반영되어 실제로 동작하는지 근거로 확인한다. 기능·계약 보존, 실제 통합·기동, 정상·경계·실패 시나리오를 과업에 맞게 수용 기준으로 정한다. 성능 개선이 목표라면 원본 기준선·대표 workload·환경·품질 조건을 정해 비교하며, 언어·도구 변경 자체를 개선 성과로 간주하지 않는다. 적용되지 않는 항목은 이유를 남기고 모든 과업에 동일한 benchmark나 실행 절차를 강제하지 않는다.

사용자가 요청한 결과를 필요한 변경과 검증으로 완성한다. 현재 산출물·범위·제약·완료 기준을 먼저 확인한다. 결과나 권한을 실질적으로 바꾸는 미결정 사항만 질문하고, 승인된 안전한 작업과 필요한 검증은 반복 승인을 요구하지 않고 수행한다.

승인은 대상·범위에만 유효하다. 목표·수용 기준·권한 확대·외부 발행·파괴적 변경처럼 기존 승인 범위를 바꾸는 결정은 사용자에게 확인한다. 사용자의 최신 정정이 기존 같은 수준 합의를 바꾸면 관련 문서에 그 결정을 남긴다.

기존 구조와 유효한 결과를 활용하고 가장 작은 충분한 변경을 한다. 원본 `seed/`는 참고 자료다. 별도 지시 없이 원본 패키지나 참고 프로젝트를 수정하지 않는다. 스킬·상시 자동화·전역 설정을 요청 범위 밖에 추가하지 않는다.

## 과업과 역할

새 개발·변경 과업은 `interview → plan → devlog → checklist` 네 문서로 의도·계획·실행·검증을 연결한다. 실제 작성 시점은 다음과 같다.

1. **의도 정립:** `interview`에 사용자 목표·범위·제약·미결정·합의를 기록한다. 이는 intent 문서의 역할이다.
2. **Planner:** interview를 읽고 구현 전에 plan과 checklist 초안을 작성한다. 완료 기준과 기본 검증 항목을 Builder에게 전달한다.
3. **Builder:** 승인 범위에서 구현하고 devlog에 실제 결정·수행·실패·현재 상태를 기록한다.
4. **Validator:** checklist를 기준으로 실제 검사하고 추가 점검·근거·결과를 보완한다. 구현 결과에 유리하게 기존 기준을 낮추지 않는다.

기본은 하나의 메인 에이전트가 역할을 순서대로 전환하는 단일 작업 루프다. 독립적인 조회는 도구로 병렬 수행할 수 있다. 별도 맥락이나 독립성의 이득이 있는 작업만 위임하고, 위임한 일을 통째로 중복 수행하지 않는다. 2계층의 단계 하나를 새 맥락의 수행자에게 맡기는 것은 맥락의 이득이 있는 위임이다.

네 문서 한 묶음이 한 루프다. 루프 안의 수정과 검증 기록은 같은 묶음에서 갱신한다. 루프는 checklist의 종료로 닫힌다. 종료는 일반 완료, 예외 승인 종료, 검토 상한이나 같은 지적의 반복으로 사람에게 넘김, 사용자가 닫기로 한 결정 중 하나다.

닫힌 루프의 대상에 작업이 더 필요하면 검토를 덧붙이지 않고 새 루프를 연다. 새 루프는 이전 루프가 닫힌 뒤에 사용자의 요청이나 승인으로만 연다. 에이전트가 스스로 열지 않는다. 같은 대상의 후속 작업은 이름을 바꿔도 새 루프로 본다. 새 루프는 네 문서를 새로 발행하고 이전 묶음을 가리킨다.

## 두 계층

과업 기록은 두 계층이다. 1계층은 `docs/`의 네 문서이고 과업의 큰 범주인 의도·계획·이력·검증을 담는다. 2계층은 `campaigns/`의 캠페인 인스턴스다. Target Project를 개선하는 과업은 대체로 오래 걸리므로 항목(cell)으로 나누고 각 항목이 단계(phase)를 밟게 한다. 항목의 상태·사건·근거 위치는 인스턴스에 두고 1계층 문서에 옮겨 적지 않는다. 그 밖의 과업은 1계층만 쓴다.

2계층은 사람의 확인 없이 오래 이어 가기 위한 것이다. 단계나 검토 회차마다 사람의 확인을 기다리지 않는다. 한 항목이 멈추면 그 항목과 같은 검증 묶음만 멈추고, 다른 묶음의 항목을 계속한다. 멈춘 항목은 모아서 보고한다. 구조와 파일 형식의 정본은 [campaigns/README.md](../campaigns/README.md)이고, 운영 규칙(언제 무엇을 하는가)의 정본은 [progress-monitor 스킬](../skills/progress-monitor/SKILL.md)이다.

## 도구 독립성과 연계

스킬은 자기 입력·수행 범위·산출물·실행 근거를 정의하는 독립 도구로 유지한다. 다른 스킬의 존재·역할·선택·호출·후속 순서를 스킬 내부에 넣지 않는다. 자체검사와 자기 산출물 수정은 구현 책임에 포함할 수 있으며 독립 검토·전체 수용과 구분한다.

메인 에이전트가 목표와 영향에 맞춰 도구를 선택하고 연결한다. 연계의 구체 대상·역할·입출력·순서·권한·실패 후 반환 조건은 과업 plan/checklist에 둔다. Rust 변환에는 rust-repack, 확실한 신규 결함 검토에는 code-review, 테스트·주석·오류·타입 등 폭넓은 관점 검토에는 pr-review-toolkit, LLM 답변·검색 문맥 평가에는 deepeval-pack, 스킬의 형식·안전·효과 측정에는 skillevaluator, AI 코드 슬롭의 감사와 범위를 정한 교정에는 anti-code-slop을 선택할 수 있다. 모든 과업에 이 도구들을 일괄 적용하지 않으며, 도구 명칭이나 특정 대상 저장소를 프로젝트 정체성으로 고정하지 않는다.

과업 책임자는 구현 완료, 자체검사, 독립 검토, 실제 통합·성능·시나리오 검사, 최종 수용의 경계를 명시한다. 동일 관련 대상·조건의 유효한 검사 근거는 역할 사이에 재사용한다. 도구가 중립적 산출물을 반환한 뒤 다음 작업을 정하는 책임은 메인에게 있다. 한 스킬의 완료를 전체 과업 완료로 확대하지 않는다.

## 독립 검증

독립 검증은 대화 이력 없이 문서와 근거만 읽는 새 맥락의 검토자가 한다. 같은 맥락에서 다시 확인한 것은 자기 점검이다.

1계층에서는 plan과 checklist 초안을 발행할 때 새 맥락 검토를 한다. 그 밖에 다음에는 별도 Validator를 추가한다.

- 사용자가 독립 검증을 요청했다.
- 권한·데이터 손실·외부 변경 등 잘못된 판단의 영향이 크다.
- 위 두 사유 중 하나를 적어 plan이 독립 검증을 완료 조건으로 정했다. 사유 없이 plan에 구현 검토를 넣지 않는다.

2계층의 항목은 기본적으로 선언한 검사 명령·기대값·근거만으로 닫는다. plan에서 다음 중 하나로 표시한 항목만 새 맥락 검토로 올린다.

- 사용자가 요청했다.
- 위와 같이 영향이 크다.
- 명령 하나로 정답을 가를 수 없어 판단이 필요하다.

수행 중의 에이전트 판단으로 표시를 더하지 않는다. 수행 중에 생긴 항목은 부모 항목의 표시와 회차를 물려받는다. 부모가 없는 새 항목에는 표시를 붙이지 않는다. 수정·검증이 되풀이해 실패해도 검토자를 더 붙이지 않고 아래 종료 규칙을 따른다.

### 검토의 종료

검토는 1회가 기본이다. 다음 회차는 앞 회차의 차단 지적을 고쳤을 때만 1회씩 더한다. 상한 3은 1회차를 포함한 전체 회차의 최대치이고, 채울 수가 아니다. 차단이 없으면 그 회차로 닫는다. 사람이 남은 차단을 받아들이면 회차를 더하지 않고 닫는다. 2계층에서는 실행기가 이것을 강제한다([campaigns/README.md](../campaigns/README.md) 끝내는 규칙).

- 지적은 차단과 비차단으로 나눈다. 차단은 완료 기준·보존 계약·권한을 어기거나 결과가 틀린 경우다. 기록의 표현이 원문과 다른 것은 차단이 아니다. 뜻이 바뀐 경우만 차단이다(아래 「기록의 판정」). 차단 지적은 어긴 기준의 위치(checklist 항목, plan 절, 규칙 줄)와 재현(명령, 또는 파일:줄과 기대·관측)을 함께 적는다. 둘 중 하나가 없으면 비차단이다.
- 차단 지적이 없으면 그 회차로 검토를 닫는다. 비차단 지적은 기록만 하고 다음 회차를 열지 않는다.
- 검토 중에는 비차단 지적을 고치지 않는다. 고칠수록 다음 회차가 볼 변경이 늘어난다. 1계층에서 고친다면 검토를 닫은 뒤 자기 점검으로 고치고 devlog에 남기며, 그 때문에 회차를 열지 않는다. 2계층에서는 캠페인 안에서 고치지 않고 브리핑의 잔여로 올린다.
- 차단 지적을 고친 뒤에만 다음 회차를 연다. 2회차부터 검토자는 앞 회차 차단 지적의 해소와, 그 수정이 바꾼 줄에서 생긴 회귀만 본다. 새 결함을 찾으라고 맡기지 않는다. 그 밖의 곳에서 늦게 발견한 문제는 비차단으로 기록해 잔여로 보고하고, 그것으로 회차를 열지 않는다. 그 잔여가 완료 기준이나 권한을 어기면 검토 통과와 별개로 checklist에 미충족으로 남기고 사용자에게 보고한다.
- 한 회차의 검토자는 plan이 사유와 함께 여럿을 정하지 않았으면 하나다. 위의 별도 Validator는 회차마다 붙이지 않고 최종 검증에 한 번 둔다. 2회차부터는 범위가 좁으므로 하나만 띄우고, 호스트가 추론 강도를 정할 수 있으면 낮게 둔다.
- 검토자에게는 차단 지적을 먼저, 비차단 지적은 중요한 것 다섯 건까지만 요청한다.
- 결론이 난 지적은 다시 열지 않는다. 검토자가 실행되지 않았으면 차단 지적이 없는 것으로 세지 않는다.
- 회차는 검토 대상 하나(문서 묶음 또는 항목)마다 센다. 차단 없이 닫힌 대상은 같은 묶음의 다른 대상이 다음 회차로 가도 다시 검토하지 않는다. 상한에 닿거나 같은 지적과 수정이 새 증거 없이 되풀이되면 통과로 치지 않는다. 남은 지적을 정리해 `ESCALATE`로 사람에게 넘기고 멈춘다. 상한을 넘겨 계속하려면 사용자의 명시 승인이 필요하다.
- 상한에 닿은 대상을 새 루프, 새 항목, 새 인스턴스로 다시 열어 회차를 되돌리지 않는다. 다시 열려면 사용자의 승인이 필요하다.

상한의 수치는 1계층은 [checklist 가이드](../docs/checklist/doc_gen_guide.md)에, 2계층은 캠페인 선언에 둔다.

이번 헌장 정립과 첫 wiki-desk 설치의 최종 검증에는 별도 Validator를 한 번 둔다.

독립 Validator는 요구·현재 변경·실행 근거를 직접 확인한다. 검토 대상 코드·헌장·수용 기준을 수정하지 않고 자기 검토 결과와 필요한 검증 임시물만 작성한다. 임시 검증 코드는 루트 `temp/` 또는 `tests/`에 둔다. 1계층의 검토 결과는 기존 checklist의 독립 검증 절에 직접 기록하거나 메인에게 반환해 같은 절에 반영한다. 2계층의 검토자는 지적 목록만 반환하고, 메인이 인스턴스의 사건 기록에 남긴다.

수정은 Builder에게 반환한다. 독립 검증자는 수정 근거를 확인해 지적을 해소하며 Builder의 `fixed` 주장만으로 닫지 않는다. 자기 점검과 독립 검증의 주체·범위를 구분한다. 별도 모델이나 에이전트 이름만으로 독립 검증을 입증했다고 하지 않는다.

### 기록의 판정

승인·결정·질문의 기록은 뜻으로 판정한다. 전사, 인용, 요약, 중계, 답 파일이 모두 여기에 든다. 판정은 검토자와 메인 에이전트가 문장을 읽고 내린다. 바이트·글자·정규식 일치를 기록의 통과 기준으로 쓰지 않는다.

- **통과**: 다음 넷이 원문과 같은 뜻으로 남아 있으면 통과다.
  - 결정: 고른 선택지나 답
  - 대상과 범위: 허용한 것과 허용하지 않은 것
  - 주체: 사용자인지 에이전트인지
  - 시점

  표현, 어순, 띄어쓰기, 문장부호, 줄바꿈, 머리 줄, 인용 꼴, 요약 여부, 뜻을 바꾸지 않는 오타는 결함이 아니다. 원문 전체 대신 원문 위치를 가리키는 포인터로 갈음해도 된다.
- **재검증(차단)**: 뜻이 바뀐 경우만이다.
  - 고른 선택지가 다르다.
  - 허용 범위가 넓어지거나 좁아졌다.
  - 승인하지 않은 것이 승인된 것처럼 적혔다.
  - 에이전트의 판단이나 적용이 사용자의 답으로 적혔다.
  - 결정이 어디에도 남지 않았다.
- 뜻이 같은 기록을 원문 그대로 다시 옮기는 정오 작업을 만들지 않는다. 뜻이 바뀐 곳만 고친다.
- 검토자에게 기록을 바이트·줄 단위로 대조하라고 맡기지 않는다. 기계 대조는 바이트가 곧 뜻인 대상에만 쓴다. 코드, 설정, 명령, 그리고 커밋·경로·버전 같은 식별자 값이 그런 대상이다.
- 사용자에게 중계한 질문에 오타가 있어도 뜻이 같으면 다시 묻지 않는다. 뜻이 바뀌었으면 다시 묻는다.

## 검증·근거·수용

검사는 다음 세 범위로 고른다.

- **필수 검사:** 합의된 완료 기준과 해당 변경에 필요한 검사.
- **영향 기반 검사:** 바뀐 동작·인터페이스·의존성·데이터 의미 때문에 선택한 검사.
- **표적 추가 검사:** 결함 후보나 불확실성을 확인하는 검사.

각 checklist 항목에 검사 명령·기대 조건·관측 결과·실행 상태·원본 근거 위치를 연결한다. 항목 하나가 관측 가능한 결과 하나다. 결과 유효성에 영향을 주는 대상·환경·데이터·검사 조건을 함께 기록한다. 실행했다면 명령과 종료 결과를 남기고 실행하지 않았다면 사유를 남긴다. 큰 로그 전문을 문서마다 복사하지 않는다.

- `PASS`: 해당 대상에서 정의한 검사를 실행해 통과했다.
- `FAIL`: 실행 결과가 기준을 위반했다.
- `NOT_RUN`: 실행하지 못했거나 아직 실행하지 않았다.
- `NOT_APPLICABLE`: 적용 대상이 아니며 이유가 있다.
- `STALE`: 관련 대상·환경·기준이 바뀌어 현재 판정에 쓸 수 없다.

파일이 그대로인지·같은지를 근거로 삼을 때 해시를 만들지 않는다. 아래 순서로 확인한다.

1. git이 그 바이트를 들고 있으면 git으로 확인한다(`git diff --quiet <기준> -- <경로>`, `git status --porcelain`, `git rev-parse <ref>:<경로>`). 근거에는 커밋이나 ref를 적는다.
   - 커밋하지 않은 변경이 그대로인지 볼 때는 그 변경을 `git diff > <기록>.patch`로 남겨 두었다가 나중에 `git diff | cmp - <기록>.patch`로 비교한다. 또는 `git stash create`가 돌려주는 커밋 ID를 근거로 적는다.
2. 비교할 원본이 손에 있으면 직접 비교한다(`cmp`, `diff`).
3. 둘 다 쓸 수 없을 때만 해시를 최후의 수단으로 쓰고, 왜 1·2를 쓸 수 없는지 적는다.

판단 기준과 예외의 세부는 anti-code-slop 스킬의 무결성 검토자 지침(`skills/anti-code-slop/references/integrity-review.md`)이다.

검사 결과, 리뷰 판단, 사용자의 수용 결정은 별개다. 문서에 규칙이 있다는 사실을 실행 강제로, 스키마·테스트 통과를 전체 정답성이나 형식 증명으로 확대하지 않는다. 검사한 성질·범위와 남은 한계를 밝힌다.

동일 대상과 관련 입력·환경·기준의 출처가 확인된 유효 결과는 재사용한다. 관련 변경·실패·의심이 없으면 같은 검사를 반복하거나 검증 범위를 넓히지 않는다. 관련 조건이 달라지거나 출처·영향 범위를 확인할 수 없으면 필요한 검사를 다시 수행한다. 독립 검증도 이 원칙을 따른다. 2계층에서 이 원칙을 적용하는 규칙(재사용, 덮임, 같은 입력의 재실행 거절)은 progress-monitor 스킬에 있다.

해시·다중 검증·별도 보안 절차·검증 자동화·형식 도구는 명시 요구 또는 객관적인 위험 근거가 있을 때만 도입한다. 해시는 그때도 위의 순서(git → 직접 비교 → 최후의 해시)를 따른다. wiki-desk가 이미 제공하는 package manifest·회귀 검사는 해당 패키지 설치의 기존 계약으로 사용한다.

일반 완료는 모든 적용 대상 checklist 항목의 통과와 필요한 독립 검증의 충족이다. 적용 제외는 사유를 확인한다. 실패·미실행이 남으면 그 상태를 보존하고 사유·잔여 위험·후속 조치를 기록한다. 사용자가 해당 대상과 잔여를 명시 승인한 경우에만 **예외 승인 종료**로 구분한다. 이를 검증 통과로 바꾸지 않는다.

## 변경 보존·중단·재개

모델 capacity는 과업 완료나 사용자 중지로 취급하지 않는다. 실제 구조화 오류·native 세션과 진행 상태를 보존하고, 승인된 같은 실행 조건에서 backoff가 있는 한정된 재시도 묶음으로 재개한다. 묶음 소진은 다음 재개 체크포인트이며 과업 전체의 호출 상한이 아니다. 모델 전환이 승인됐다면 실제 실행 모델에 귀속하고 원래 평가 프로필의 성공으로 합치지 않는다. 권한·인증·정체성·불명 실행 상태는 capacity로 추정하지 않는다. 대화형 호스트의 자체 모델 선택은 제공된 제어 수단의 범위에서만 다루며, 지원되지 않는 설정·API로 우회하지 않는다. 협업 에이전트에서 같은 오류가 나면 호스트가 제공하는 동일 에이전트 재개 수단을 사용하고, backoff 뒤 저장된 산출물·실행 상태부터 확인한다. 원본 검사나 끝난 작업을 다시 실행하지 않으며, 논리 에이전트 ID를 native CLI 세션 ID로 꾸미거나 모델을 조용히 바꾸지 않는다.

변경 전에 대상 파일과 기존 수정 상태를 확인하고 사용자 변경·무관한 파일·과거 근거를 보존한다. 기존 설치본이 있으면 차이를 검토하며 소유나 충돌이 불분명한 부분을 덮어쓰거나 지우지 않는다. 실패한 부분부터 고치고 유효한 기존 결과는 유지한다.

같은 지적과 반박이 새 증거 없이 반복되거나 필수 환경·권한이 없으면 남은 지적·시도·원인·다음 결정을 기존 devlog/checklist에 남긴다. 2계층에서는 그 항목의 사건 기록에 남긴다. 실행할 수 없으면 `BLOCKED`, 목표·설계·위험 수용 결정이 필요하면 `ESCALATE`로 보고한다. 설정된 한도를 지키며 중단을 PASS나 사용자 승인으로 간주하지 않는다.

중단 시 실제로 수행한 변경·완료·미완료·재개 지점을 남긴다. 재개 시 현재 파일·실행 상태를 확인하고 남은 작업과 영향을 받은 검사부터 수행한다. 일반 파일 작업에 범용 백업·저널·롤백 프레임워크를 일괄 추가하지 않는다.

## 완료 보고

결과부터 짧게 보고하고 근거와 미완료·한계만 덧붙인다. 실행하지 않은 검사나 확인하지 않은 승인을 만들지 않는다. 합의된 완료 기준을 충족하면 추가 작업 없이 종료한다.
